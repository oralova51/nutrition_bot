# DOMAIN ANALYSIS

## Виртуальный консультант по питанию

---

## 1. УЧАСТНИКИ (STAKEHOLDERS)

### Primary Users (Основные пользователи)
- **Клиент** - конечный пользователь системы, участник программы коррекции фигуры в студии

### Secondary Users (Вторичные пользователи)
- **Администратор студии** - управляет данными клиентов, имеет доступ к статистике и ответам клиентов для контроля качества программы, формирует отчеты
- **Специалист по коррекции фигуры** - получает информацию о соблюдении клиентом рекомендаций по питанию для корректировки программы тренировок

### External Systems (Внешние системы)
- **Telegram** - канал доставки сообщений (коммуникационный шлюз для отправки уведомлений клиентам)
- **Open API** - интеграция с внешними сервисами (опционально: синхронизация данных с приложениями калорийности)

### System Components (Компоненты системы)
- **AI Engine** - ядро системы для анализа данных питания, выявления проблемных паттернов и генерации персонализированных рекомендаций

## 2. DOMAIN ENTITIES (СУЩНОСТИ ПРЕДМЕТНОЙ ОБЛАСТИ)

### Основные сущности

**Client (Клиент)**
- Идентификатор клиента
- ФИ
- Telegram ID (контактные данные)
- Telegram username (опционально, обновляется при активации ссылки)
- Email (опционально, для уведомлений администратору)
- Дата регистрации
- Дата последнего взаимодействия (lastInteractionAt) (ДОБАВЛЕНО: ФТ-9, ФТ-11; см. adminAPI.md)

**Course (Курс)**
- Идентификатор курса
- Название программы
- Длительность (дни)
- Каталог доступных целей (Goal Template), может быть несколько на курс
- Дата начала и окончания

**Goal (Цель)** (уточнено: разделена на шаблон и персональный экземпляр, см. п.3.1)
- Идентификатор цели
- Тип цели (снижение веса, набор мышечной массы, улучшение метаболизма, улучшение здоровья)
- Целевые показатели (например, минус 10 кг, плюс 5 кг мышц)
- Исходные параметры (вес, объемы)
- Временной горизонт
- Связь с Client Enrollment (персональный экземпляр цели для конкретного периода участия клиента)

**Client Enrollment (Запись клиента о курсе)**
- Идентификатор записи
- Связь с клиентом
- Связь с курсом
- Дата начала
- Дата окончания (плановая)
- Статус (активна, пауза, завершена, отменена)

### Сущности подключения (ФТ-1)

**Enrollment Link (Ссылка подключения)** (ДОБАВЛЕНО: см. adminAPI.md, roadmap 3.1)
- Идентификатор ссылки
- Связь с Client Enrollment
- Уникальный код (payload для Telegram deep link, префикс `enr_`)
- Дата создания
- Дата истечения (createdAt + 7 дней)
- Дата использования (usedAt, заполняется при успешной привязке telegramId)
- Telegram ID пользователя, активировавшего ссылку (опционально)
- Статус (active, used, expired, revoked)

**Enrollment Link Attempt (Попытка использования ссылки)** (ДОБАВЛЕНО: лог ФТ-1)
- Идентификатор попытки
- Связь с Enrollment Link
- Дата и время попытки
- Telegram ID (если известен)
- Результат (success, expired, already_used, invalid_code, enrollment_cancelled)

### Сущности для отслеживания питания

**Nutrition Diary (Дневник питания)**
- Идентификатор записи
- Связь с клиентом
- Связь с Client Enrollment (ДОБАВЛЕНО: без этого нельзя корректно разделить данные при продлении курса, см. п.3.1)
- Дата и время приема пищи
- Описание блюда/продукта
- Приблизительная калорийность
- Наличие прикрепленного фото
- Статус записи (заполнена, ожидание данных, требует уточнения) (ДОБАВЛЕНО: атрибут отсутствовал, хотя используется в ФТ-5 и ФТ-22)

**Habit (Привычка)**
- Идентификатор привычки
- Описание (например, "Пить воду перед едой", "Избегать сладких напитков")
- Связь с клиентом
- Статус отслеживания (активна, неактивна)
- Частота выполнения (ежедневно, определенные дни недели)

**Notification Settings (Настройки уведомлений)**
- Идентификатор настройки
- Связь с клиентом
- Время отправки напоминаний (часы и минуты)
- Частота напоминаний (ежедневно, через день, еженедельно)
- Типы включенных уведомлений (рекомендации, напоминания о дневнике, еженедельные отчеты, ежедневная вечерняя сводка)
- Статус (включено/отключено)
- Причина отключения (user_request, inactivity) (ДОБАВЛЕНО: нужно для разграничения ФТ-10 и ФТ-12)

### Сущности взаимодействия с клиентом

**Questionnaire (Анкета)**
- Идентификатор анкеты
- Набор вопросов для анализа пищевых привычек (см. `anketa.md`)
- Связь с клиентом
- Связь с Client Enrollment
- Ответы клиента
- Статус (in_progress, completed) (ДОБАВЛЕНО: нужно для ФТ-2, напоминание при незавершённой анкете)
- Номер текущего вопроса (на каком вопросе остановился клиент) (ДОБАВЛЕНО: для текста напоминания «Вы остановились на вопросе {X}»)
- Дата и время последнего ответа (ДОБАВЛЕНО: отсчёт N часов до напоминания)
- Дата и время последнего напоминания (ДОБАВЛЕНО: контроль повторных напоминаний)
- Дата прохождения (заполняется при status=completed)
- Результаты анализа (выявленные проблемы)

**Recommendation (Рекомендация)**
- Идентификатор рекомендации
- Тип рекомендации (совет о конкретном продукте, привычке, режиме питания, калорийности)
- Приоритет (критическая, высокая, средняя, низкая)
- Связь с анализом дневника питания или анкеты
- Дата и время создания
- Статус (отправлена, прочитана, применена, отклонена)
- Связь с клиентом

**Message (Сообщение)**
- Идентификатор сообщения
- Связь с клиентом
- Тип сообщения (рекомендация, напоминание, напоминание об анкете, вечернее напоминание, вечерняя сводка, отчет, информационное, …)
- Категория (транзакционное / отключаемое клиентом) (ДОБАВЛЕНО: нужно разграничить, чтобы итоговый отчёт и запрос обратной связи не блокировались отключением уведомлений по ФТ-12, см. также замечание к Functional_Requirements.md)
- Содержание
- Дата отправки
- Статус доставки (отправлено, доставлено, прочитано, delivery_failed)
- Канал доставки (enum: Telegram, WhatsApp, Max) (ИЗМЕНЕНО: было жёстко "Telegram", nonFR.md требует готовности к другим каналам)

**Reminder (Напоминание)**
- Идентификатор напоминания
- Связь с клиентом
- Тип напоминания (заполнить дневник, проверить рекомендацию)
- Расписание (время отправки)
- Статус (активно, неактивно, выполнено)

**Feedback (Обратная связь)**
- Идентификатор обратной связи
- Связь с рекомендацией
- Связь с клиентом
- Оценка полезности (1-5)
- Комментарий клиента
- Дата создания
- Отметка "применена ли рекомендация"

### Аналитические сущности

**Report (Отчет)**
- Идентификатор отчета
- Связь с клиентом
- Связь с Client Enrollment (ДОБАВЛЕНО: отчёт формируется за конкретный период участия, при продлении курса отчётов должно быть несколько, привязанных к разным enrollment)
- Период анализа (дата начала и конца)
- Статистика по дневнику питания (средняя калорийность, макронутриенты: белки, жиры, углеводы)
- Соблюдение рекомендаций (процент)
- Выявленные проблемные области
- Динамика изменений (в сравнении с предыдущим периодом)
- Тип отчета (ежедневный evening summary, еженедельный, ежемесячный, итоговый)

**Progress (Прогресс)**
- Идентификатор записи о прогрессе
- Связь с клиентом
- Связь с целью (персональный экземпляр Goal конкретного Client Enrollment)
- Временная метка (дата измерения)
- Текущие метрики (вес, объемы, самочувствие)
- Процент достижения цели
- Комментарий (опционально)

**AI Model Log (Лог модели ИИ)** (ДОБАВЛЕНО: отсутствовала сущность, хотя бизнес-правило 6 требует переобучения на основе Feedback)
- Идентификатор записи
- Версия модели/промпта
- Дата обновления
- Основание для обновления (агрегированная низкая оценка Feedback за период)
- Комментарий аналитика

## 3. КРИТИЧЕСКИЙ АНАЛИЗ И ЗАМЕЧАНИЯ

### 3.1 Новые проблемы, найденные при повторном анализе

1. **Противоречие в связях Goal** - в исходной ERD-диаграмме Goal был подвешен одновременно и к Client Enrollment (1:1), и к Course (1:M) без пояснений. Исправлено: Course хранит каталог шаблонов целей, а конкретный Client Enrollment создаёт персональный экземпляр Goal с исходными параметрами именно этого клиента.

2. **Nutrition Diary, Report и Progress не были привязаны к Client Enrollment** - при продлении курса (ФТ-18) у клиента появляется несколько enrollment'ов, и без явной привязки невозможно корректно разделить статистику по периодам, как того требует итоговый отчёт (ФТ-14) и архивирование истории (ФТ-23). Добавлена связь.

3. **Nutrition Diary не имел атрибута "статус"** - при этом ФТ-5 и ФТ-22 явно оперируют статусами "ожидание данных" и "требует уточнения". Атрибут добавлен.

4. **Message.«Канал доставки» был захардкожен как Telegram** - nonFR.md прямо требует готовности подключить WhatsApp и Max в будущем, поэтому канал должен быть перечислимым полем, а не константой.

5. **Матрица прав доступа была неполной** и содержала противоречие по Feedback (см. п.3.2), матрица дополнена.

6. **Отсутствовала сущность для версии AI-модели** - бизнес-правило "AI Engine должен переобучаться на основе Feedback с низкой полезностью" не может быть реализовано и проверено без журнала версий/оснований для обновления модели.

### Проблемы в исходном документе (из предыдущей версии, актуальны):

1. Client Enrollment отсутствовал в первой версии - нужна явная сущность для связи между клиентом и курсом
2. Notification Settings не имел связи с Client
3. Habit не имел связи с Client
4. Feedback был недоопределен
5. Recommendation не отслеживал применение
6. Message и Reminder перекрывались функционально

## 5. МАТРИЦА ПРАВ ДОСТУПА (ДОПОЛНЕНО)

| Сущность              | Клиент                | Администратор                              | Специалист                |
| ---------------------- | --------------------- | ------------------------------------------- | -------------------------- |
| Client                 | Просмотр своих данных | Полный доступ                                | Просмотр связанных данных |
| Enrollment Link        | Нет доступа           | Генерация, просмотр, отзыв, regenerate (ФТ-1) | Нет доступа               |
| Enrollment Link Attempt| Нет доступа           | Просмотр лога попыток                        | Нет доступа               |
| Course                 | Просмотр своего курса | Полный доступ                                | Просмотр                   |
| Goal                   | Просмотр своей цели   | Полный доступ                                | Просмотр                   |
| Nutrition Diary        | CRUD                   | Просмотр (анонимизированно)                  | Просмотр связанных        |
| Recommendation         | Просмотр, оценка       | Просмотр статистики                          | Просмотр связанных        |
| Report                 | Просмотр своего        | Просмотр всех                                | Просмотр связанных        |
| Progress               | Просмотр своего        | Просмотр всех                                | Просмотр связанных        |
| Feedback (оценка звёздами) | Создание           | Просмотр статистики (агрегированно)          | Просмотр связанных        |
| Feedback (комментарий при 1-3 звёздах) | Создание | Просмотр персонально, с указанием клиента (ФТ-16) | Просмотр связанных |
| Notification Settings  | Изменение своих         | Просмотр всех, массовое отключение при необходимости | Нет доступа        |
| Habit                  | CRUD                   | Просмотр всех                                | Просмотр связанных        |
| Message                | Просмотр своих          | Просмотр статуса доставки, повторная отправка | Нет доступа               |

Примечание: строка Feedback разделена на две, так как агрегированная оценка (звёзды) и персональный негативный комментарий имеют разный уровень доступа для администратора, это прямо следует из ФТ-16 и снимает противоречие с прежней версией матрицы.

## 6. КРИТИЧЕСКИЕ БИЗНЕС-ПРАВИЛА

1. Рекомендация должна быть создана только на основе Nutrition Diary или Questionnaire
2. Progress может быть создан только для активного Client Enrollment
3. Notification Settings должны быть инициализированы при создании Client
4. Feedback должна быть создана максимум через 24 часа после Recommendation
5. Message в Telegram отправляется асинхронно
6. AI Engine должен переобучаться на основе Feedback с низкой полезностью, каждое такое обновление фиксируется в AI Model Log
7. Напоминание о незавершённой анкете отправляется только при status=in_progress и только если с момента последнего ответа клиента прошло N часов (ФТ-2)
8. Enrollment Link одноразова по активации: после успешной привязки telegramId статус → used, повторное использование запрещено; до активации ссылка может открываться многократно в пределах 7 дней (см. adminAPI.md §2)
9. На один активный Client Enrollment допускается не более одной Enrollment Link со статусом active
